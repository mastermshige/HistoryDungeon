## このSpec.mdの書き方（重要）

### AIが補ってくれること

「あなたのゲームをどう動かしたいか」を **自然言語で書いてください**。以下は書かなくてOK:

- クラス名・ファイル名 → Core 規約から AI が自動命名
- API 名・メソッドの引数 → 動きを自然言語で書けば AI が推論
- DOTween の `Ease.OutBack` などの値 → 「勢いよく」「ふわっと」のような雰囲気で書けばよい
- ParticleSystem の細かい設定 → 「コマ送りのように順に切り替えて」のような説明でよい

技術用語が分かるなら補足してもOK（例: 「勢いをつけて飛び出す（`Ease.OutBack` 的な動き）」）。分からない場合は書かなくていい、AI が自然言語から判断する。

### 設計上の重要原則（必ず守る）

本ゲームは CoreRules.md の MVP 構成（**Logic ← Presenter → View**）に従います。Spec を書くときの注意:

- **「Logic が View を直接操作する」設計は書かないこと**（古い MVC 的な書き方は避ける）
- Logic は View を一切知らない（純粋ロジックのみ）
- Presenter が Logic の通知を受けて View 操作に変換する
- 複数の同種要素（ブロック多数・敵キャラ複数体など）も、Logic は **「論理的なインデックス」** で扱い、Presenter が物理的な View 配列にマップする
- Spec には「インデックスベースで何が起きるか」「Presenter がどう View に伝えるか」を書く（`IXxxView` interface を Logic 配下に置く設計は書かない）

### 効果音・BGM

サウンドは **1箇所に集約して管理する** 設計にしたい。各オブジェクトに個別に音をセットして回るのではなく、SE/BGM をまとめて持つ場所（ScriptableObject を想定）を1つ用意し、そこを窓口にする。

**1. 管理構造（どこに音を持つか）**

- SE/BGM のオーディオクリップは、専用の ScriptableObject に **まとめて1箇所で持たせる**
- ブロックやパドルなど個別のオブジェクト側にはクリップを持たせない（音を持つ場所と鳴らす対象を分離する）

**2. ユーザー操作（どう設定するか）**

- ScriptableObject の中に「**ボールを跳ね返した時の音**」「**ブロックを崩した時の音**」「**ゲーム開始時のBGM**」のように、用途ごとの枠（項目）を用意しておく
- ユーザーは Inspector でその枠に対象のオーディオクリップを **ドラッグでセットするだけ** で設定が完了する（コードを触らない）

**3. 実装ロジック（どう鳴らすか）**

- 個別のオブジェクト側で `AudioSource.Play()` を直接呼ぶのではなく、**集約された場所のロジックを通して** 適切な音を呼び出す
- 「どの場面でどの枠の音を鳴らすか」はこのロジックが解決し、再生処理を一手に引き受ける（音の追加・差し替えがこの ScriptableObject だけで完結する）
- CoreRules.md の MVP に従い、音を鳴らすトリガーは Presenter 側（Logic の通知を受けて再生を依頼する）に置く。Logic は音を直接知らない

ゲームの各要素を「**何ができるか・どう動くか**」を自然言語で書く。クラス名や API 名は書かない。

### 例: ブロック

```
- 弾がぶつかると崩れる（崩し判定がオフの間は無反応）
- 出現の動き: ステージ開始時にふわっと姿を見せ、表示スプライトを "通常" に差し替える
- 崩れる動き: 鋭く素早く弾けて消滅し、スプライトを "崩れ" に差し替える
- ヒビの動き: 耐久が残る当たりではヒビだけ入り、スプライトを "ヒビ" に差し替える
- 崩し判定のオン/オフを外側から制御できる
- 演出の発生位置を外側から問い合わせできる
```

### 例: ブロック配置制御

```
- ステージ開始時にブロックを格子状に並べる
- 並べ方（行数・列数）はパラメータで渡せる
- 並んだ各ブロックは **論理インデックス（0〜N）** で区別する。Logic は番号だけで扱い、番号と実際のブロック View の対応付けは Presenter が受け持つ
- ブロックが崩れたら Logic が番号付きで通知し、Presenter がそれをスコアや崩し演出へ橋渡しする
```
